# Android Catan — Code Audit (13 October 2026)

Status: **in progress, not verified stable**. Build 002 compiles but crashes on the Samsung phone. All changes below are staged in the development branch, **not** in a new tested APK.

## Scope checked

- All 75 Java files in `app/src/main/java` inspected with structural/suspicious-pattern checks, including all 20 action objects, 28 framework files, 12 game models, 11 core/animation files and 4 rendering files.
- All 22 layout XML files checked for balanced tags and duplicate locally declared IDs.
- Focused review of launch sequence, legacy network setup, map rendering and hit testing, CPU setup/actions, game rules, Longest Road, deck handling, package/signing/versioning and GitHub Actions.
- Build 002 debug/signed APK ZIP entries compared: app resource/code bytes are unchanged during post-build signing; extra entries are META-INF signature files. This does **not** prove runtime health.
- No local Android SDK/emulator is installed here. **No** post-fix compilation, Android runtime test or device crash log is available.

## Defects fixed in development branch

1. **Probable launch crash:** Original configuration screen always queried the phone IP address, even after INTERNET permission was removed in Build 002. Removed obsolete network lookups; no networking required for local games.
2. **Smart CPU setup deadlock:** Used `validRoadPlacement(...)` overload without the required starting settlement ID; could never find a valid initial road. Fixed five-argument legality check.
3. **Actual opponent type:** Default app configuration was selecting the three random 'Dumb Computer' bots, so smarter CPU changes were unused. Changed three defaults to 'Smart Computer'.
4. **Development deck:** `getRandomDevCard()` regenerated all 25 cards when exhausted. It now keeps the finite deck and rejects purchases when empty.
5. **Longest Road:** Old algorithm treated graph traversal vertices as road length and prematurely `break`-ed the four-player loop. Replaced with pure-Java unique-edge trail traversal and obstacle/tie handling; refreshes after road and settlement changes. Added six JUnit regression tests (**tests not yet executed**).
6. **Future build workflow:** Removed dependency on a nonexistent encrypted keystore/Actions secret. Owner-approved branch builds will run JVM tests + assemble one debug APK, followed by private permanent-key signing outside GitHub. Ordinary dev commits do not build.
7. **Permanent update numbering:** Gradle uses GitHub run number as Android versionCode. Stable package identity retained. Same permanent signing key must be retained across all release-to-user APKs.

## Important unresolved gaps

- **Build 003 must compile and run on Samsung first.** The probable crash source is not proven without a stack trace.
- No player-to-player CPU trading or negotiated counteroffers (classic Catan feature).
- Road Building development card currently adds brick/lumber instead of awarding two cost-free roads; rule is incorrect.
- Year of Plenty currently awards two copies of only one resource, instead of allowing any two resources.
- Some legacy game action paths rely on UI/CPU legality checks rather than consistently enforcing rules in the engine.
- CPU still has primitive turn handling and long sleeps; no completed AI win-rate benchmark or 3 calibrated difficulty settings.
- Full game saves/resume not implemented.
- Original app's vast configuration/gameplay XML is functional only insofar as prior build compiled. It is not yet proven readable/usably responsive on Samsung.
- Other classic-rule edges (robber/victim selection, bank resource availability, one-development-card-per-turn restrictions, piece limits, tie behaviour) need automated gameplay tests and complete-device games.
- Confirm that the signed Build 003 can install over the permanently signed Build 002 without losing data. The permanent signing key and passphrase must be backed up securely outside ephemeral working storage.

## No-cost preflight test coverage and build discipline

No additional GitHub Actions run has been triggered by this audit. The next approved APK build will execute `:app:testDebugUnitTest` and `:app:assembleDebug` in **one** workflow run; if tests fail, the job fails. APK then needs stable signing before delivery.

## On-device acceptance plan

1. Launch config page without crash and start 1-human/3-smart-CPU game.
2. All initial settlements and roads placed; CPU finishes setup; no indefinite waiting.
3. Whole island and ports visible; every touch hits the intended tile/intersection.
4. Resource collection, building/city upgrades, robber, development cards and current-player scoring.
5. Test Longest Road five-road award, tie retention and interruption by rival settlement.
6. Finish full game and ensure winner is correctly declared.
7. Verify install-over update and test basic persistence when a save system is introduced.

**Verdict:** Source review has caught critical regressions, but the game cannot truthfully be called perfect or classic-rules-complete yet.
